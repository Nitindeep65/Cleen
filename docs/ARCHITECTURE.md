# CLEEN Architecture

## 1. Purpose and Scope

CLEEN is an equipment cleaning log for pharmaceutical operations. The application manages equipment, cleaning records, and an auditable history of field-level changes.

The target stack is:

- Backend: Node.js, TypeScript, Express
- Database: PostgreSQL with Prisma ORM
- Frontend: React and TypeScript

The repository contains an Express/TypeScript backend with Prisma-backed runtime services, PostgreSQL schema/migration/seed artifacts, and a React/TypeScript frontend. In-memory storage is limited to explicit test mode.

## 2. Domain Model

### Equipment

| Field | Type | Rules |
| --- | --- | --- |
| `id` | UUID/string | Primary key, generated server-side |
| `name` | string | Required, non-empty |
| `code` | string | Required, unique |
| `status` | enum | `ACTIVE`, `INACTIVE`, or `MAINTENANCE` |
| `createdAt` | timestamp | Server-managed |
| `updatedAt` | timestamp | Server-managed |

### CleaningRecord

| Field | Type | Rules |
| --- | --- | --- |
| `id` | UUID/string | Primary key, generated server-side |
| `equipmentId` | UUID/string | Required foreign key to `Equipment` |
| `cleanedBy` | string | Required, non-empty |
| `cleanedAt` | timestamp | Required valid timestamp |
| `method` | string | Required, non-empty |
| `notes` | string/null | Optional |
| `status` | enum | `COMPLETED`, `IN_PROGRESS`, or `FAILED` |
| `createdAt` | timestamp | Server-managed |
| `updatedAt` | timestamp | Server-managed |

### AuditLog

| Field | Type | Rules |
| --- | --- | --- |
| `id` | UUID/string | Primary key, generated server-side |
| `cleaningRecordId` | UUID/string | Required foreign key to `CleaningRecord` |
| `changedBy` | string | Required actor identity |
| `changedAt` | timestamp | Server-managed event timestamp |
| `changes` | JSON array | Field-level `{ field, oldValue, newValue }` entries |

## 5. API Contract

All routes are prefixed with `/api`. Successful responses return JSON. Errors use a consistent shape:

```json
{
  "error": {
    "message": "Human-readable message",
    "details": []
  }
}
```

Validation errors return `400`, missing resources return `404`, conflicts such as duplicate equipment codes return `409`, and unexpected failures return `500` without leaking internals.

### Equipment

| Method | Path | Purpose | Success |
| --- | --- | --- | --- |
| `GET` | `/api/equipment` | List equipment, optionally filtered by status/search | `200` |
| `GET` | `/api/equipment/:id` | Retrieve one equipment item | `200` |
| `POST` | `/api/equipment` | Create equipment | `201` |
| `PATCH` | `/api/equipment/:id` | Update equipment fields | `200` |
| `DELETE` | `/api/equipment/:id` | Delete equipment without records | `204` |

Equipment create requires `name`, `code`, and optionally `status` with a documented default. Equipment update accepts a non-empty subset of mutable fields. IDs are generated by the server.

### Cleaning Records

| Method | Path | Purpose | Success |
| --- | --- | --- | --- |
| `GET` | `/api/equipment/:equipmentId/cleaning-records` | List records for equipment | `200` |
| `POST` | `/api/equipment/:equipmentId/cleaning-records` | Create a record | `201` |
| `GET` | `/api/cleaning-records/:id` | Retrieve one record | `200` |
| `PATCH` | `/api/cleaning-records/:id` | Update mutable record fields | `200` |
| `GET` | `/api/cleaning-records/:id/audit` | Retrieve audit history | `200` |

Create requires `cleanedBy`, `cleanedAt`, and `method`; `notes` and `status` follow the documented defaults. The client must not provide old values or audit entries.

### Audit History

`GET /api/cleaning-records/:id/audit` returns audit entries in ascending `changedAt` order, with `id`, `cleaningRecordId`, `changedBy`, `changedAt`, and field-level `changes`.

## 6. Pagination and Filtering

`GET /api/equipment/:equipmentId/cleaning-records` accepts:

- `page`, default `1`, positive integer
- `limit`, default `10`, positive integer with a maximum of `100`
- `status`, optional valid CleaningRecord status

The target response is:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 10,
    "total": 0,
    "totalPages": 0,
    "hasNextPage": false,
    "hasPreviousPage": false
  }
}
```

The backend must apply the same equipment and status filters to the count and data queries, use database-level `skip = (page - 1) * limit` and `take = limit`, and order deterministically by `cleanedAt` descending with `id` as a tie-breaker. A page beyond the last page returns an empty data array with accurate metadata. A missing equipment ID is `404`; an existing equipment item with no matching records returns an empty `200` response.

Runtime pagination uses Prisma `skip`/`take`; test mode uses equivalent in-memory slicing to keep unit tests deterministic.

## 7. Audit Trail Strategy

Every CleaningRecord create and update writes an AuditLog entry in the same database transaction as the record mutation.

The diff engine compares the persisted old record to the proposed new record and tracks only mutable business fields:

- `cleanedBy`
- `cleanedAt`
- `method`
- `notes`
- `status`

It excludes IDs, foreign keys, audit metadata, and server-managed timestamps unless a future requirement changes this policy. A create event records each supplied/defaulted business field with `oldValue: null`. An update records only changed fields. `null` is distinct from a non-null value; structured values use stable deep equality.

The actor comes from the authenticated/request context or the explicitly documented local-development actor convention. It must never be accepted as a client-provided old value. The server sets `changedAt`.

The runtime computes audit changes from persisted old and resulting new records; clients cannot submit audit changes.

## 8. Validation and Security

- Validate JSON bodies and query parameters at the API boundary.
- Reject unknown enum values, invalid timestamps, empty required strings, malformed IDs, invalid pagination, and empty PATCH bodies.
- Enforce unique equipment codes at the database and service layers.
- Use environment variables for `DATABASE_URL` and other runtime configuration; never commit credentials.
- Use parameterized Prisma queries and avoid raw SQL unless required and safely parameterized.
- Return safe error messages without stack traces or database details in production.
- Add authentication/authorization only if required by the assignment; actor capture must still be explicit and testable.

## 9. Testing Strategy

Prioritize meaningful behavior tests:

- Diff engine: one field, multiple fields, no changes, null-to-value, value-to-null, structured values.
- Audit integration: create, update, actor/timestamp, retrieval, transaction failure behavior.
- Pagination: first/middle/last/beyond-last pages, empty results, status filtering, invalid values, count/data consistency.
- API: equipment CRUD, cleaning-record create/update/list, audit endpoint.
- Frontend: form validation, loading/error/empty states, pagination, mutation refresh, and audit rendering where the test setup supports it.
- End-to-end smoke workflow: create equipment, create record, verify audit, update record, verify diff and refreshed history.

## 11. Current Risks and Open Questions

- PostgreSQL migration and seed have been applied locally; runtime services use Prisma persistence.
- The API rejects the legacy `pageSize` parameter and requires `limit` for pagination.
- A concrete authentication mechanism/actor source is not specified; local development needs a documented actor convention until authentication exists.
- Frontend/API integration and browser-level tests remain a coverage gap.
- Repository hygiene should be checked from the actual Git checkout before submission.
